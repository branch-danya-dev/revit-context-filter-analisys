# ContextFilter — функциональные требования

> Нормализованное представление подтверждённых функциональных требований из двух исходных ТЗ и фактически реализованного продукта.

## Источники

Требования получены из двух документов заказчика, которые рассматриваются как последовательное развитие одной задачи, а также из точечных уточнений в общении.

Этот документ не копирует ТЗ построчно. Он объединяет повторяющиеся формулировки в один requirement set и отделяет продуктовые требования от архитектурных решений.

## FR-01 · Запуск ContextFilter

Пользователь должен иметь возможность запустить ContextFilter из Revit и получить доступ к интерфейсу фильтрации.

Базовый поддерживаемый способ — запуск из Ribbon. Дополнительные способы быстрого вызова могут быть доступны как пользовательская настройка, но не должны быть обязательны для основного сценария.

## FR-02 · Выбор рабочего контекста

Система должна позволять фильтровать элементы в ограниченном рабочем контексте.

Поддерживаемые реализованной системой варианты:

- Active View;
- Entire Document;
- Current Selection.

Если перед запуском пользователь сформировал выборку, система должна уметь использовать её как входной набор для дальнейшей фильтрации.

## FR-03 · Навигация Category → Family → Type

После получения контекста пользователь должен видеть структуру используемых элементов и иметь возможность сузить набор через:

```text
Category
→ Family
→ Type
```

Список должен отражать элементы текущего рабочего контекста, а не абстрактный перечень всех возможных семейств проекта.

## FR-04 · Выбор параметра

Пользователь должен иметь возможность выбрать параметр, доступный для элементов текущего контекста / выбранной группы элементов.

Система должна поддерживать параметры экземпляра, типа и системные свойства, представленные как фильтруемые признаки.

## FR-05 · Выбор или ввод значения

Пользователь должен иметь возможность выбрать существующее значение параметра и, где сценарий это допускает, задать значение вручную.

## FR-06 · Логические условия

Система должна поддерживать комбинацию условий фильтрации, включая AND и OR.

Сложные условия не должны менять смысл отдельного атомарного условия.

## FR-07 · Корректность фильтра по типу

При фильтрации по конкретному типу система не должна включать элементы других типов, которые не удовлетворяют заданному условию.

Это требование происходит из явно описанного дефекта reference workflow в первоначальном ТЗ.

## FR-08 · Динамическое выделение

При включённой пользователем соответствующей возможности система может подсвечивать текущий найденный набор в Revit по мере изменения filter intent.

Функция не должна быть единственным способом увидеть результат фильтрации.

## FR-09 · Selection actions

Система должна поддерживать действия над selection, включая предусмотренные реализованным продуктом сценарии:

- Replace;
- Add;
- Exclude.

Исключение должно быть доступно только тогда, когда существует исходная выборка, из которой имеет смысл удалять найденные элементы.

## FR-10 · Temporary visibility actions

Система должна позволять применить найденный набор к текущему виду:

- Hide;
- Isolate;
- inverse isolation;
- reset temporary visibility state, если оно управляется текущим workflow.

## FR-11 · Native Revit filter

Система должна уметь создавать штатный Revit filter для тех filter definitions, которые могут быть корректно выражены средствами Revit.

Невозможность преобразовать некоторый сложный client-side filter в native filter не означает, что сам filter intent недействителен.

## FR-12 · Presets

Пользователь должен иметь возможность сохранить часто используемое filter intent и применить его повторно.

## FR-13 · Template presets

Пользователь должен иметь возможность сохранить структуру фильтра без привязки к конкретным значениям, чтобы выбрать значения заново в другом контексте.

## FR-14 · Ошибка должна быть видима пользователю

Если запрошенное действие не может быть выполнено, пользователь должен получить краткое понятное уведомление о причине.

## FR-15 · Исходные элементы не изменяются фильтрацией

Применение ContextFilter не должно удалять, перемещать или произвольно изменять элементы BIM-модели.

## FR-16 · Повторное использование панели

Пользователь должен иметь возможность выполнять последовательные итерации поиска без необходимости каждый раз заново проходить полный ручной Revit workflow.

## Не зафиксировано как функциональное требование

Исходные документы не определяют:

- конкретный внутренний формат `FilterDefinition`;
- Clean Architecture;
- использование snapshots или inverted index;
- механизм `ExternalEvent`;
- конкретный persistence format пресетов;
- алгоритмы caching / chunking.

Это решения реализации и системного проектирования, а не customer requirements.
